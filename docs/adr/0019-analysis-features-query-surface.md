# 0019. Analyses are queried through features resolved at ingest

Status: accepted, built

## Context

A meta-analysis pools analyses, chosen by what their papers' extraction records say: the groups' medical condition, the task, the two sides of the contrast, whole brain or not, the study design. A record analysis names those things by local id (`measure: "mea_bold"`, `groups[].group`, `tasks[]`, cells through the model's factor levels to conditions), so no single row answers them. `feature_filter` runs a jsonpath over the whole stored record per filter: it cannot follow the ids, two `analyses[]` filters need not match the same analysis, and it returns studies. Measured on 100 local records (88 KB compressed, 370 KB raw each), one jsonpath took 168 ms, about 100 s at the corpus's 61k records; fetching and decoding the records for a query in Python would take about 13 minutes. Queries have to answer in under a second.

## Decision

The ingester resolves each record analysis once, at upload, into a row of `analysis_features` (`neurostore/ingest/analysis_features.py`): one row per analysis of the paper's current pipeline Study whose key the paper's latest record describes, written from that record; the inverse half of a sign split takes its original's row with the contrast's sides swapped. Every upload rewrites the paper's rows, a merge rewrites the keeper's, and `manage backfill-analysis-features` rewrites them all. Columns are typed (text, arrays of ids and of study_schema enum values, booleans, `n`), NULL where the record says nothing, with B-tree, GIN and trigram (`pg_trgm`) indexes. The record's own wording, for results and annotation columns, is in `analysis_feature_displays`, so scans read only what they filter on.

`POST /analysis-queries/` (`neurostore/analysis_query.py`) compiles a query to one SQL condition over that table: criteria combine with AND, a list or `any` is OR, `all` and `none` are AND and NOT within a field, `or` takes sub-queries, and `when_silent` on each criterion says whether an analysis the record is silent about matches. Text matches whole words with `*` and `?` wildcards and needs three consecutive letters or digits; species and other enum-valued fields match exactly. The response counts the selected studies and analyses (`metadata.total_count`, `metadata.analysis_count`) and lists the selected studies a page at a time, like the list endpoints (`page`, `page_size`, `paginate: false` for all), each with as much as `detail` asks for: its ids only, its selected analyses, or (the default) their features too; with `funnel`, also each criterion's kept, dropped and silent counts, one indexed count per criterion. `PUT /annotations/{id}` takes `analysis_query` to write the selection (a boolean column, `included` by default) and chosen features into the notes, which Compose's `filter` reads.

A normalized feature (medical condition, task, contrast key, contrast set) is searched the way OMOP CDM keeps `concept_id` beside `source_value` and FHIR token search offers `:below` and `:text`. Each has `_ids` (the mapped entries), `_ancestor_ids` (those and every ancestor, written at ingest), its wording and labels as text where it has wording, and `_unmapped`, true when the record states the feature and nothing in it mapped. That is not silence: a healthy group's condition and a value read as an absence are silent. A criterion says which path it takes: `ids` match through the ancestors unless `descendants: false`, `text` is a pattern, and either may match; `when_unmapped` (`exclude` by default, `include`, `text`) decides the unmapped analyses. Each result says how it matched each normalized criterion, and the funnel counts the unmapped. A task's family is written as an entry of its own, and a contrast key (`family|...`) or set (`family#n`) names its family, so those closures need no ontology. MONDO and ONVOC ancestors, labels and synonyms come from the releases study_schema's vocabulary manifest pins (the ones the normalizer mapped against), which `manage sync-vocabulary-releases` loads into `concepts` and `concept_ancestors` after checking each file's sha256 (`neurostore/ingest/concepts.py`); a deploy runs it and reloads only when the pin moves, then backfills. Entries are read by the manifest's vocabulary names, neutral or legacy (`astra canonical task`, `ns-pond contrast set <fit>`), so records written before the rename and after it read alike. Each row names the releases its ids resolve against (`vocabulary_releases`), and the drift report lists the ids a loaded release lacks, the rows written before their release was loaded, and the rows read against another release or fit. Direction is part of a contrast term: ns-pond writes a key with the sides it reads as target and baseline and the sign apart, and a set member's orientation against the set's medoid, so a term is the key or set itself where the analysis states it that way and `<term>:reversed` where it states the opposite; a query lists both to take either. `role` narrows a medical condition's ids to the items ns-pond gave that role. Each side of a contrast has its own columns (`contrast_positive_*`, `contrast_negative_*`), from the factor levels of the cells signed onto it: its groups' health and medical conditions (with ancestors, as the analysis's), its timepoints' `relation_to_intervention`, its arms' `arm_kind`, and the facets its contrast keys put on it (a target or `vs:` token's `name:value` atoms or `~wording`, or a baseline's kinds, swapped for a `:reversed` key). `contrast.positive` and `contrast.negative` take criteria on those (`has_patients`, `medical_condition`, `timepoint`, `arm_kind`, `facet`, and `name` for the side's text, which a bare text criterion in their place is shorthand for), so "patients > healthy controls" is a query: of the 847 rows staging's 198 records give, 40 put only patients on the positive side and only controls on the negative, and 38 the reverse. `analysis_terms` keeps each term's label and parent for `/analysis-terms/`. Rows carry the `mapping_tool` of every entry their ids came from, and an annotation export freezes the canonical query, the selected analysis ids and those tools in the annotation's metadata.

## Consequences

- Measured on 950k rows (the resolver's output for 100 real records, copied at random, with zipf-distributed MONDO and task ids), local pg17 with 128 MB shared_buffers, warm: medical condition, task, contrast, design, silent-inclusive, `none`/`all` and `or` queries in 5–196 ms, a broad one (whole brain, BOLD, human: 275k analyses) in 648 ms. With the funnel, 340–685 ms, except where an early criterion keeps most of the table (2.3 s for the broad query, 2.9 s for `none` over medical conditions), since each step counts what it keeps.
- A resolver change needs the backfill; the rows are derived, never edited.
- A query can be restricted to papers (`base_study_ids`) or pipeline studies (`study_ids`), any number of each; the counts, results and funnel then cover the restricted set, so an empty query with `base_study_ids` returns those papers' features. Added for clients that judge a known candidate set, such as autonima's screening.
- Results are studies, each with its selected analyses, so each id appears once and a page never splits a study. `detail: studies` with `paginate: false` gives every selected study's id for a studyset; the default `detail` gives every record too. Neither the listing nor a scope has a cap. Measured on the 2026-11-09 production dump (244,365 analyses, 62,313 studies) on beast, one uvicorn worker: a page of 20 studies 0.03 s (page 3000, 0.21 s); every study's id 0.32 s and 3.3 MB; every study with its analyses 1.9 s and 24 MB; every study with features 9.2 s, 283 MB and 3.3 GB peak RSS in the worker. That last listing reads rows through Core, the display as text for orjson and arrays as `text[]`: through the ORM it took 13 s.
- Features come from the latest record only. Curators' field claims are not read yet.
- `analysis_features` is served, unlike the truth layer it is read from (`tests/test_truth_layer.py`).

## Rejected

- **Extending `feature_filter`.** No id resolution, filters not bound to one analysis, studies not analyses, ~100 s per filter.
- **A jsonpath over `pipeline_analysis_results`.** Binds criteria to one analysis but cannot reach measures, groups or tasks.
- **One JSONB features document per analysis.** 2x slower on broad queries in the prototype, larger, and its keys would not be the query's vocabulary.
- **The display values in the features table.** It was 1085 MB against 382 MB without them, and broad counts read every page.
- **The funnel as one pass with a FILTER per step.** It ran every text pattern on every row (9.5 s); with the patterns as joined match sets it no longer did, but the pass itself read the whole table for every query (1.2–2 s), and joining those sets into the selection defeated its bitmap OR (50 ms to 500 ms).
- **The funnel on every response.** It is most of a broad query's cost; it is there when asked for.
- **Ancestors written into each `normalized` entry by the normalizer.** A study_schema field, a re-normalization and re-upload of every record for each ontology release, and ~15 more ids per mapping in every record; the table needs a load and a backfill.
- **A side's features as one tagged array** (`group:healthy`, `mondo:…`, `valence:negative`) or JSONB. One GIN index instead of ten, but a side's criteria would not be the analysis's criteria (`descendants`, `when_unmapped`, `when_silent` per field), and silence could not be told apart from a value.
- **An `orientation` parameter on contrast criteria.** Direction belongs to the term, so a saved query or an export names what it selected.
- **Reading a criterion's value as an id when it looks like one** (no spaces, a colon or `#`). A term id and a wording can look alike, and the response could not say which path matched.
- **Implicit filters** (whole brain only, human only), as pondie's `Selection` defaults: an API that drops ROI analyses unasked surprises; the response echoes the whole canonical query instead.
